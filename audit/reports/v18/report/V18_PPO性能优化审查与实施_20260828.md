# V18 PPO 性能优化审查与实施记录

日期:2026-08-28

## 1. 背景与测量结论

V18 PPO 常用配置(`riichi_ppo_v1/configs/v18_ppo.yaml`:
`num_workers=12 × envs_per_worker=32, games_per_update=2048, update_epochs=2,
DDP learner_gpus=2`)下,一次完整迭代(rollout + update)实测约 600s+
(`checkpoints/train_riichi_v18/ppo/performance.jsonl` 最近两条记录:
迭代1 = rollout 301s + update 365s;迭代2 = rollout 266s + update 323s)。
用户反馈的 800-900s 对应更大局数/机器负载场景。

### 1.1 Rollout(≈265-300s)耗时分解(worker 均值,来自 performance.jsonl)

| 阶段 | 每 worker 总耗时 | 占比(近似) |
| --- | --- | --- |
| inference/rpc_wait | ≈191-214s | 主要等待(等待推理 actor 返回) |
| inference actor full_forward(GPU) | 双 rank 各 ≈170s(enqueue 计时) | 推理本身 |
| model_state_prepare(Python 编码) | ≈38-42s | 第二大 |
| current_state_assembly(仅 Python 装配) | ≈25-28s | 编码大头 |
| critic_feature_encode | ≈9-10s | 编码 |
| env step_batch + event sync | ≈8-9s | 环境 |
| 其余(解码头/GAE/打包) | ≈5s | 小 |

推理 actor 侧每 rank:`full_forward_rows_mean≈91`,`dispatches≈7925-8828`,
`dispatch_timeout≈100%` —— 即 8ms 超时触发的小批(≈91 行),GPU 每批固定
开销占主导(其余相关生产数据见下文 microbenchmark)。

### 1.2 Update(≈323-365s)耗时分解(ppo/ 前缀,汇聚值)

| 阶段 | 总量 | 每 minibatch |
| --- | --- | --- |
| backward | 144s(1932 批) | 74.5ms |
| model_forward | 90s(1932 批) | 46.6ms |
| collate_soa_gather(prefetch 线程) | 25.4s | 13.1ms(与 GPU 重叠) |
| collate_h2d | 7.3s | 3.8ms |
| 诊断/裁剪/optimizer | <0.8s | — |

数据规模:每 update ≈1.48M transitions × 2 epochs ≈2.97M 样本,平均 110
tokens/样本;bucketing 后 padding 仅 ≈0.6%,分桶已很有效。

### 1.3 GPU 事实(备注)

本机 GPU 枚举(torch 视角):0/1/2/3 为 L20 46GB,4 为 T400 4GB。
当前训练用 `CUDA_DEVICE=0,1` 占用两块 L20;另外两块空闲 L20 对应
CUDA 下标 2、3。**维护者决定维持 2 卡占用**,不启用推理独占卡/多 GPU
扩展,本书不将其列为优化路径。

## 2. 已实施的优化

### 2.1 Rust 下沉:完整 Actor 批装配 `assemble_current_state_batch`

- 新增 `RiichiEnv/riichienv-python/src/current_state_encoding.rs` 的
  `assemble_current_state_batch`(PyO3),一次性完成:
  Shared/Analysis 行 + `SEP_ACTIONS` + 每个合法动作的 O/D Query 行穿插、
  query/action-id 元数据与 241 维合法掩码的整批物化。
- `riichi_ppo_v1/model/current_state.py::encode_batch` 改为调用该 Rust
  函数,删除逐决策的 numpy 分配/拷贝 Python 装配循环。
- 实测(32 env 回合级):`encode_batch` 每回合 ≈5.6ms → ≈2.9ms,
  `bridge.prepare` 每回合 ≈9.3ms → ≈6.5ms;12 个 worker 并行后,
  rollout 侧的 CPU 准备时间(42s/worker)可下降约 30%,直接改善推理
  actor 的批次等待与 GPU 利用率。
- 已用真实环境 964 个决策与旧 Python 装配逐位等价校验(全部字段一致),
  并跑通 `tests/unit` + `tests/integration` 共 190+ 用例。

### 2.2 DDP: bootstrap 结束后关闭 `find_unused_parameters`

- `PPOLearner` 新增 `_rebuild_ddp_without_unused_when_ready`:
  critic bootstrap 只有前 2 个 update,之后所有参数都进入 loss;此时重建
  DDP 包装(`find_unused_parameters=False`),消除 PyTorch 官方警告的
  「每次 backward 多一次 autograd 图遍历」开销(≈2000 minibatch/update)。
- bootstrap 期仍保持 `True`,避免未参与 loss 的 actor/shared 参数触发
  DDP 报错(已用真实 DDP 验证 `False` 在 bootstrap 语义下会报错)。

### 2.3 推理批处理策略

- `_target_workers()` 支持 `inference_batch_target_workers: -1` 禁用
  「按 worker 数触发」的小批冲刷,只按行数/超时;`v18_ppo.yaml` 将
  `inference_batch_wait_ms` 8.0 → 16.0 以换取更大批次(GPU 每批固定
  开销主导,已用 idle L20 microbenchmark 确认 B=94→188 时吞吐
  1.28M→1.81M tokens/s)。
- 按维护者决定:**保持 2 卡占用**,不做推理独占卡/多 GPU 扩展
  (曾实验的 `inference_actor_devices`/显式 `device_index` 已回退,
  `train.py` 恢复原 `num_gpus=1` 自动分配路径)。

### 2.4 配置契约

- 删除配置里与代码无关的 `checkpoint_force_first_updates` 键,并同步
  删除 `test_v18_ppo_config.py` 中对应断言(该键无运行时语义)。

## 3. 建议的下一步(未实施,按预期收益排序;维持 2 卡占用)

1. **微调推理批次等待**:16ms 仍需 A/B(`inference_batch_wait_ms` 12/16/24
   各跑 1-2 个 update,看 `rollout/wall_s` 与 `dispatches`)。若 24ms 后
   `dispatches` 明显下降且 GPU 事件耗时上升不明显,可继续上调。
2. **StateTokenEmbedding 向量化**:当前 `argsort + tolist()` 每 forward
   有 GPU→CPU 同步与逐类别 Python 循环;实测嵌入层占 forward ≈24%。
   本仓实验的「逐类别 bool-mask + nonzero」备选实现在真实类别数下未跑赢
   现实现,需换「类别常量表 + 预计算索引」或直接把它整体写成 CUDA/Rust
   才划算;同时可解锁 `torch.compile`(当前因 `nonzero`/`item()` graph
   break,`torch.compile` 实测无收益)。
3. **`critic_feature_encode` 下沉 Rust**:≈10s/worker,可与 2.1 同批做。
4. **`_native_batch_inputs`/legal JSON 链路精简**:`query_native` ≈2ms/回合
   与 `legal_action_json` ≈0.5ms/回合仍跨多轮 PyO3;若把
   `prepare_decisions`+`prepare_encoding_facts`+装配合并为单一 Rust 入口,
   每回合可再省 ≈2.5ms。
5. **worker 内部流水线**:当前 6 worker/rank 各自串行「prepare→RPC→step」,
   若把 32 env 拆成 2-4 个独立流(各配独立 state machine),在途请求数
   翻倍,批次更大;改动较大,需要保确定性与线程安全,列 P2。
6. **环境侧**:`step_batch` 每步都重建 4×env 个 Observation PyObject
   (≈5ms/worker 总量)与 `walls()` 拷贝;可加「仅返回 delta/事件」的
   Rust 轻量接口,收益中等。
7. **数值**:可试 `torch.set_float32_matmul_precision("high")`(TF32),
   对 fp32 残余路径加速;须验证训练稳定性,未默认开启。
