### 2.2 输出解码——SFT 路径 PASS，bridge 路径 FAIL（新发现）

新增只读脚本 `audit/reports/v18/scripts/v18_decode_roundtrip.py`：对 12 个真实 kyoku 的
**7150 个合法 action id** 做「id → Rust `decode_actions` → 解码」往返：

| 解码路径 | 失败数 | 说明 |
| --- | --- | --- |
| B1：规范 JSON 匹配（`sft/data.py` 同路径） | **0 / 7150** | 每个 id 解码回 MJAI 后经 canonical key 找到唯一合法 Action，再 `action_groups.action_id` 重映射回原 id |
| B2：`observation.select_action_from_mjai`（`bridge.decode` 同路径） | **27 / 7150** | 全部为 chi/pon；典型 `{"consumed":["E","E"],"pai":"E","type":"pon"}` |

**发现 V18-DEC-1（P1，输出解码错误，范围=未迁移的 PPO/rollout bridge 路径）**：

- **现象**：`BatchedStateBridge.decode()`（`bridge.py:160-174`）采用
  `state_machine.decode_actions(...)` → `observation.select_action_from_mjai(mjai)`。当底层
  `Action.consume_tiles` 把**被鸣牌也包含在内**（长度 3：如本 fixture rec2/rec4/rec5/rec6 的
  pon/chi，全 12 局共 27 例），`action_jsons` 的规范化会把 consumed 缩减为 2（MJAI 协议形式），
  状态机 `possible_actions` 存的是规范化模板，`decode_actions` 返回规范化模板；但
  `mjai_select.rs::consumed_matches` 是与 `Action.consume_tiles` **逐项等长比较**（3 vs 2 → None）。
- **证据**：`rec2 seat2 id=157`：`consume_tiles=[108,108,108]`、raw to_mjai consumed 3 张、
  `select(raw)` 成功、`select(canonical)` 返回 None；27 例均集中在该表示的回放。
- **影响**：SFT 数据链不受影响（B1 走代表匹配，0 失败；`encode_kyoku` 本身也不调用
  `select_action_from_mjai`）；但**未来 PPO/rollout 一旦迁移到 `bridge.prepare/decode`，
  含此类副露的决策将无法把模型输出的 action id 解码回 env 动作**。
- **建议**：二选一——(a) `mjai_select::select_action` 对 chi/pon/daiminkan 在 consumed 长度差 1
  且等于手牌数时容忍（把 called tile 并入比较）；或 (b) `bridge.decode` 改用与 SFT 相同的
  canonical-key 代表匹配（或 Rust 返回带 source index 的直接映射，配合 `action_ids_with_source_indices`）。
  建议先加回归测试：`test_bridge_decode_roundtrip`（含 called-in-consume 的 pon/chi 样例）。

### 2.3 模型输出 → 动作

- 模型 `policy_logits` 为 241 维（非法恒 -inf）；固定种子模型下 862 个真实决策 top-1 全部 ∈ legal

## §3 Q3：Python 侧性能审查（V17 → V18）

新增 `audit/reports/v18/scripts/v18_perf_review.py`（cProfile + 计时，本机 CPU）测量结果：

| # | 发现 | 等级 | 证据/测量 | 建议 |
| --- | --- | --- | --- | --- |
| V18-PERF-1 | 训练 collate 每批执行**全 Python 语义校验** `assert_actor_input_semantics`（B8 新增），含逐 token × 逐字段 Python 循环 | P3 | 131 决策 × 13,938 token = **144 ms**（≈10.4 µs/token）；按 `v18_sft.yaml` batch_size=512 外推 **≈565 ms/批**，相比 5.8M 模型一个 GPU step（毫秒~几十 ms 级）是主导 CPU 开销 | 校验移到 DataLoader worker 进程/离线一步完成；或将域/结构校验向量化（numpy 按 kind 批量比较），训练中仅保留 `target∈legal` 等 O(1) 检查；`validate_semantics` 已可配置，但默认 True |
| V18-PERF-2 | precompute `_accumulate_field_statistics` 新增**逐 token × 逐字段 Python 域检查**（旧版只做 query 向量化检查） | P3 | 862 决策 95,291 token = **273 ms**（≈2.9 µs/token）；60% 数据集 ≈100 万决策 → **≈317 s**（8 worker 下 ≈40 s 墙钟，且与编码串行） | 按 kind 用 numpy 批量域比较；或把域统计并入 Rust 编码器返回（已有 `field_statistics` 语义） |
| V18-PERF-3 | `encode_batch` 的 Python 装配层占总耗时 **≈52%**（9.9–10.4 ms / 19.6 ms，131 决策）；每动作对一次 `np.vstack` 追加 + `_action_row` Python 构造 | P3 | cProfile：`_action_row` 2136 次调用、2 kyoku 中 `encode_batch` cumtime 95 ms。**注**：审查期间工作区出现一处未提交的 `current_state.py` 微优化（预分配数组替代逐动作 vstack，见 §7），复测后 Python 装配仍 ≈10.4 ms——说明剩余开销主要在 `_action_row` 的逐动作 Python 构造与逐行循环，而非 vstack 复制 | 预分配 `[B,T_max,32]` 后按行 `slice` 赋值（已存在于工作区，未提交）；进一步把 SEP_ACTIONS/query 行拼接下沉到 `prepare_current_state_batch` 同一次 Rust 调用（当前模块 doc 明确「Action Query 由 Python 拼接」，属设计回退点） |
| V18-PERF-4 | Rust 批编码器**不释放 GIL**：`prepare_current_state_batch`、`prepare_encoding_facts` 函数体无 `py.detach/allow_threads`；而 `apply_events_batch`（manager.rs:87）与 `analyze_encoding_yaku_batch`（encoding_facts.rs:852）均释放 | P3（违反 V17 spec「Rust 计算释放 GIL 并优先持久线程池」） | 静态检查：`prepare_current_state_batch: body uses GIL release = False`；逐 obs 顺序循环（无 rayon） | 批编码包 `py.detach`（数据已拷入 Vec，无 Python 交互）；批内如需并行再加 rayon/线程池 |
| V18-PERF-5 | `sft/data.py::encode_kyoku` 每决策**调用两次 `action_jsons(observation)`**（batch 循环 + templates），且对每个合法动作做 Python `json.loads/json.dumps` 代表匹配；Rust 已有 `action_ids_with_source_indices` 直接映射（仅 `bridge.py` 使用） | P3 | cProfile：2 kyoku 中 `action_jsons` 262 次调用；`json.dumps 2610 / json.loads 2740`；`_normalized_action_json` 218 次 | 数据链改用 `action_ids_with_source_indices` 复用 `legal_actions()` 对象（同 bridge），消除二次 action_jsons 与 JSON 匹配 |

**总体判断**：V18 的主语义计算（shanten/analysis/query answers/current-state 行）仍在 Rust 批编码器内，
相比旧 V18 前身（Python `analyze_action_queries` 逐动作 + 逐决策 `encode_snapshot_rows`）是**净下降**；
但没有把 V17 已经建立的「Python 只做 PyO3 边界」纪律贯彻到底——上面的 1/2/3 都是**新引入的
Python 逐 token/逐动作工作**，4 是 V17 明确要求但 V18 新编码器未遵守，5 是既有但可用 Rust 直接映射消除的冗余。
